Login via the application\n2. JWT token is returned in response\n3. Include token in all API requests\n\n### Using the Token\n\n```bash\ncurl -X GET \"http://localhost:8080/api/v1/audit-logs\" \\\n  -H \"Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...\"\n```\n\n### Token Requirements\n- **Location:** Authorization header\n- **Format:** `Bearer {token}`\n- **Expiry:** Check your login response\n- **Roles Required:** ADMIN, SUPER_ADMIN, or SUPERVISOR\n\n---\n\n## Response Format\n\nEvery API response follows this standard structure:\n\n### Success Response (200, 201)\n\n```json\n{\n  \"success\": true,\n  \"message\": \"Operation completed successfully\",\n  \"data\": {\n    // Response data\n  },\n  \"timestamp\": \"2026-09-01T10:35:00\",\n  \"code\": 200\n}\n```\n\n### Error Response (400, 404, 500, etc.)\n\n```json\n{\n  \"success\": false,\n  \"message\": \"User-friendly error message\",\n  \"error\": \"Detailed error information\",\n  \"timestamp\": \"2026-09-01T10:35:00\",\n  \"code\": 400\n}\n```\n\n### Response Fields\n\n| Field | Type | Description |\n|-------|------|-------------|\n| success | boolean | Whether the request succeeded |\n| message | string | Human-readable message |\n| data | object/array | Response payload (null on error) |\n| error | string | Detailed error info (only on error) |\n| timestamp | datetime | When response was generated |\n| code | integer | HTTP status code |\n\n---\n\n# Audit Logs API\n\n**Base Endpoint:** `/api/v1/audit-logs`\n\n**Purpose:** Track and audit all system changes\n\n## 1. Create New Match\n\n### Request\n\n```http\nPOST /api/v1/matched-transactions\nContent-Type: application/json\n\n{\n  \"incomingTransactionId\": 100,\n  \"outgoingTransactionId\": 101,\n  \"description\": \"Daily settlement from branch A\",\n  \"note\": \"Auto-matched by reconciliation system\"\n}\n```\n\n### Request Body\n\n| Field | Type | Required | Description |\n|-------|------|----------|-------------|\n| incomingTransactionId | integer | Yes | ID of incoming transaction |\n| outgoingTransactionId | integer | Yes | ID of outgoing transaction |\n| description | string | No | Match description |\n| note | string | No | Internal notes |\n\n**Rules:**\n- Incoming and outgoing transactions must be different\n- Each transaction can only be part of one match\n- Status automatically set to PENDING\n\n### Example\n\n```bash\ncurl -X POST \"http://localhost:8080/api/v1/matched-transactions\" \\\n  -H \"Authorization: Bearer YOUR_TOKEN\" \\\n  -H \"Content-Type: application/json\" \\\n  -d '{\n    \"incomingTransactionId\": 100,\n    \"outgoingTransactionId\": 101,\n    \"description\": \"Branch settlement\",\n    \"note\": \"Auto-matched\"\n  }'\n```\n\n### Response (Success - 201 Created)\n\n```json\n{\n  \"success\": true,\n  \"message\": \"Resource created successfully\",\n  \"data\": {\n    \"id\": 1,\n    \"incomingTransactionId\": 100,\n    \"outgoingTransactionId\": 101,\n    \"incomingAmount\": 1000.00,\n    \"outgoingAmount\": 1000.00,\n    \"status\": \"PENDING\",\n    \"matchedAt\": \"2026-09-01T10:35:00\"\n  },\n  \"code\": 201\n}\n```\n\n### Response (Error - 400 Bad Request)\n\n```json\n{\n  \"success\": false,\n  \"message\": \"Invalid request\",\n  \"error\": \"Incoming and outgoing transaction must be different\",\n  \"code\": 400\n}\n```\n\n### Response (Error - 409 Conflict)\n\n```json\n{\n  \"success\": false,\n  \"message\": \"One or both transactions are already part of an existing match\",\n  \"code\": 409\n}\n```\n\n---\n\n## 4. Update Match Status\n\n### Request\n\n```http\nPATCH /api/v1/matched-transactions/{matchId}/status\nContent-Type: application/json\n\n{\n  \"status\": \"CONFIRMED\",\n  \"note\": \"Approved by supervisor after verification\"\n}\n```\n\n### Path Parameters\n\n| Parameter | Type | Required | Description |\n|-----------|------|----------|-------------|\n| matchId | integer | Yes | Match ID to update |\n\n### Request Body\n\n| Field | Type | Required | Description |\n|-------|------|----------|-------------|\n| status | string | Yes | New status: PENDING, CONFIRMED, or DISPUTED |\n| note | string | No | Update notes |\n\n**Status Transitions:**\n- `PENDING` → `CONFIRMED` (supervisor approval)\n- `PENDING` → `DISPUTED` (issues found)\n- `CONFIRMED` → `DISPUTED` (reversal if error found)\n- `DISPUTED` → `CONFIRMED` (after resolution)\n\n### Example\n\n```bash\ncurl -X PATCH \"http://localhost:8080/api/v1/matched-transactions/1/status\" \\\n  -H \"Authorization: Bearer YOUR_TOKEN\" \\\n  -H \"Content-Type: application/json\" \\\n  -d '{\n    \"status\": \"CONFIRMED\",\n    \"note\": \"Verified and approved\"\n  }'\n```\n\n### Response\n\n```json\n{\n  \"success\": true,\n  \"message\": \"Match status updated successfully\",\n  \"data\": {\n    \"id\": 1,\n    \"status\": \"CONFIRMED\",\n    \"note\": \"Verified and approved\",\n    \"incomingTransactionId\": 100,\n    \"outgoingTransactionId\": 101\n  },\n  \"code\": 200\n}\n```\n\n---\n\n## 5. Authentication & Security\n\n✅ **DO:**\n- Store tokens securely (secure cookies, local storage with caution)\n- Include token in Authorization header\n- Refresh tokens before expiry\n- Use HTTPS in production\n- Rotate tokens regularly\n\n❌ **DON'T:**\n- Expose tokens in URLs\n- Store tokens in plain text\n- Share tokens between users\n- Log tokens in error messages\n\n## 2. Error Handling\n\n✅ **DO:**\n- Check `response.success` field\n- Log error details for debugging\n- Retry on temporary errors (500, 503)\n- Handle specific HTTP status codes\n- Display user-friendly error messages\n\n```javascript\nif (response.success) {\n  // Process data\n} else {\n  if (response.code === 401) {\n    // Re-authenticate\n  } else if (response.code === 404) {\n    // Show \"Not found\"\n  } else if (response.code >= 500) {\n    // Retry later\n  }\n}\n```\n\n## 3. Rate Limiting\n\n✅ **DO:**\n- Implement request throttling\n- Cache responses when possible\n- Batch requests when creating multiple resources\n- Use pagination for large datasets\n\n## 4. Data Validation\n\n✅ **DO:**\n- Validate input before sending\n- Check for required fields\n- Validate transaction IDs exist\n- Verify status transitions are valid\n\n## 5. Logging & Monitoring\n\n✅ **DO:**\n- Log all API calls (method, endpoint, status)\n- Monitor response times\n- Track error rates\n- Alert on repeated failures\n- Keep audit trail of changes\n\n```javascript\nfunction logApiCall(method, endpoint, status, duration) {\n  console.log(`[${new Date().toISOString()}] ${method} ${endpoint} - ${status} (${duration}ms)`);\n}\n```\n\n## 6.
